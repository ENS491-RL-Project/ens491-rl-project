## What H-7 can show, and what it cannot

After H-6 the supported claim is reuse, not speed on a single task: `{2,1} solve_doorkey` costs
49–56k env steps of its own and 661–667k including its children, against 300–450k for flat PPO
(H-6.8 figures; the composite's update size was changed in H-6.8 and flat PPO's was not).

`env_steps_own < env_steps_total` holds by construction. "Reusing a skill is cheaper than
retraining it" is therefore arithmetic, not a finding, and H-7 must not present it as one. The
empirical content of C2 is these four measurements and nothing else:

| | Question | Measured by |
|---|---|---|
| **R1 Transfer** | Does a frozen skill work, untouched, inside a task it was never trained in? | F29 rows: `{1,1} unlock_door` inside UnlockPickup, and inside BlockedUnlockPickup after the blocker is moved |
| **R2 Marginal cost** | Given the library, is a new task cheaper than learning it flat? | `env_steps_own` of the nodes created for the task vs flat PPO's steps to STABLE on that task |
| **R3 Amortisation** | Over the whole curriculum, does the hierarchy's cumulative cost fall below flat PPO's, and at which task? | the cumulative table of H-7.8 |
| **R4 Depth reuse** | Does reusing an intermediate composite help? | T9b (level 3, reuses `unlock_pickup`) vs T9a (level 2, same skills, no intermediate node); a depth-4 stack |

## Constraints (from CLAUDE.md and v2; every task includes them)

- Observation pipeline `ImgObsWrapper → FlattenObservation → ChannelNormalize`, `(147,)` float32. Never `CnnPolicy`.
- A frozen node is never modified, for any reason. A node's `children` are immutable. Only FROZEN nodes may be children.
- Every node's reward comes from its own `goal` predicate, never from the env's reward.
- Masking is goal-only; `initiation` is metadata and the strict-mask ablation. `max_decisions` is mandatory.
- `timeout >= max(child.timeout)`, and a root's `timeout <= env.max_steps` (F13), validated at creation.
- Stabilisation: SR ≥ 0.90 **and** Wilson 95% lower bound ≥ 0.80 on the 50 fixed stopping seeds, twice
  in a row; one held-out evaluation at freeze, which is the only number quoted. **No per-node stopping
  rule**: a node that cannot meet this is not frozen, and that is reported.
- **Composites train in small updates and are evaluated one update apart (V11):** `n_steps = 64`
  (64 × 8 envs = 512 decisions per PPO update) and `eval_every = 512` for every composite, baseline
  option sets included. "Twice in a row" then means two different policies, the earliest possible
  STABLE is 1,024 decisions, and `decisions_to_stable` has a resolution of 512 instead of 2,048.
- `DummyVecEnv` only. PPO hyperparameters otherwise unchanged, and unchanged in full for primitives
  and flat PPO: `n_steps=256, batch_size=256, n_epochs=4, lr=3e-4, gamma=0.99, gae_lambda=0.95,
  clip_range=0.2, ent_coef=0.01`, 8 envs.
- Design changes go into `docs/ENS491_Target_Architecture_v2.md` first (Part A), in their own commit.
- Interpreter: `C:\Users\memir\miniconda3\envs\ens491\python.exe` (`conda` is not on PATH). CPU only.

**A.6 §11 reporting, two fields added to every composite's report.**

composites use `n_steps = 64`, because one composite step is a whole child execution and 2,048 of

```
  initiation  door_approach_blocked()

{2,2} unlock_pickup                            composite, n=2 (derived), m=2
  children      ({1,1} unlock_door, {0,4} pickup_box)
  goal          carrying("box")

  env           MiniGrid-UnlockPickup-v0, no reset hook
  timeout       288          # F13 window is 240..288
  max_decisions 8

{2,3} blocked_pickup_a                         composite, n=2, m=3      (T9a)
  children      ({0,5} move_blocker, {1,1} unlock_door, {0,4} pickup_box)
  goal          carrying("box")
  initiation    all_of(door_locked(), door_approach_blocked())
  env           MiniGrid-BlockedUnlockPickup-v0, no reset hook
  timeout       576
  max_decisions 12

{3,1} blocked_pickup_b                         composite, n=3, m=1      (T9b)
  children      ({0,5} move_blocker, {2,2} unlock_pickup)
  goal / initiation / env / timeout   as blocked_pickup_a
  max_decisions 8
```

Two new library functions, both with a spec string so they enter `spec_hash`:

- `door_approach_blocked()` in `src/skills/predicates.py`, spec `"door:approach_blocked"`: true iff a
  ball is orthogonally adjacent to the door. It is the negation of `door_approach_clear()` when a
  door exists and false when there is none.
- `relocate_blocker()` in `src/envs/subgoal_env.py`, spec `"relocate_blocker"`: if the layout has a
  ball, move it to a cell drawn with the env's own `_rand_int` from the free cells reachable from the
  agent that are not orthogonally adjacent to the door; a no-op when there is no ball, so one hook
  serves both envs. It reproduces the state `move_blocker` leaves, which `clear_blocker()` does not
  (it deletes the ball, and V7 is exactly about the ball still being in the room). Raise
  `UnsuitableLayout` if no such cell exists.

`randomize_carrying` on `move_blocker` is deliberate. Under goal-only masking a parent may pick
`unlock_door` first; `get_key` then succeeds (V6), `open_door` cannot, and control returns with the
key in hand. A `move_blocker` that only ever started empty-handed would make that mistake
unrecoverable. **Fallback, not a stop:** if this node is not stable within 600,000 steps, retrain it
with `hook = randomize_agent_pose(anchor=None)` only (a new spec string, hence a new hash), and
record that a wrong first pick is then unrecoverable in T9.

Baselines, each identical to the node it is compared with in goal, timeout, pipeline, PPO config, 8
envs, stopping seeds and held-out seeds:

```
{0,B} flat_unlock_ppo            Unlock-v0              goal door_open()       timeout 240   budget 1,500,000  eval_every  50,000
{0,B} flat_unlockpickup_ppo      UnlockPickup-v0        goal carrying("box")   timeout 288   budget 3,000,000  eval_every 100,000
{0,B} flat_blocked_ppo           BlockedUnlockPickup-v0 goal carrying("box")   timeout 576   budget 3,000,000  eval_every 100,000
{1,B} flat_unlockpickup_options  UnlockPickup-v0        children (get_key, open_door, pickup_box)
                                                        goal carrying("box")   timeout 288   max_decisions 12  budget 40,960 decisions
```

**Budgets are fixed here and are never extended.** 3,000,000 is about four times the hierarchy's
cumulative cost through DoorKey (661–667k) and 6.7–10 times flat PPO's own cost on DoorKey-6x6. A
run that is not stable at its budget is reported as `> budget (not stable)` with the best success
rate it reached. `eval_every` keeps a failing policy's evaluation cost (50 episodes × timeout =
12,000, 14,400 or 28,800 env steps) under 30% of the steps between evaluations.

# How the result is worded

These are rules for the summary and for any report text drawn from it.

- Never "the hierarchy learns faster" without naming which of own / total / cumulative is meant.
- R2 and R3 are stated with the flat baseline's number or its censoring: "`> 3,000,000`, best SR 0.xx", never "flat PPO fails".
- If A5 took the rebuild branch, T9 is described as **rebuilt, not reused**, and R1's answer for
  BlockedUnlockPickup is "no". That is a finding about the limit of reuse with frozen primitives
  (V7), and it is reported as prominently as a success would be.
- On the strict-order tasks the strict-mask random control is expected to tie on success rate. Say so
  in the same sentence as the composite's score.
- A composite below 0.90 is reported with its `chain_ceiling`.
- A success-rate gap over a control is never reported alone (V12). Each composite's summary line
  carries the mechanism measure beside it: the sequence of children selected on the held-out
  episodes, as counts per distinct sequence, written to the report as `selection_sequences`.
