## Reading, by the plan's table

UnlockPickup: no seed STABLE and best stopping success rate 0.00 (< 0.10) on all three, so
**memory alone does not explain the flat 0/50, for this architecture and budget.**
DoorKey (not a gate): the LSTM needed more steps on every seed (550–750k against 300–450k).

## What it does and does not show

- The memoryless flat result on UnlockPickup is not a memory limit of the kind a 64-unit LSTM
  removes; against it the hierarchy's `{2,2} unlock_pickup` is 49/50 held-out at about 2.4M env steps
  per run (W1b-1). That answers the open question's "does flat need memory" for this recurrent
  variant. It does not show that no flat learner with memory can solve the task.
- PPO hyperparameters were not tuned for the recurrent policy, one architecture, three seeds,
  argmax evaluation, no frame-stack arm.
