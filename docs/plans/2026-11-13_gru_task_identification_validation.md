# GRU-Based Task Identification: Experimental Validation

## Overview

Candidate 1 (Recognition Track R-2) focuses on supervised GRU-based task identification from observation sequences generated by pretrained PPO policies in MiniGrid.

The supervised known-task identification and sequence-length ablation experiments have been completed, on three training seeds.

## Methodology

- **Dataset:** 5,500 episodes collected from 11 pretrained PPO policies (500 each, env seeds 20000–20499, deterministic execution).
- **Classification:** 9 task classes, with related PPO policies mapped to shared task labels (`flat_unlock_ppo` and `unlock_door` → `unlock`; `flat_doorkey_ppo` and `solve_doorkey` → `doorkey`).
- **Input:** Observation-only sequences (147-dimensional observations); every window ending at each step of an episode, shorter at the start.
- **Model:** Single-layer GRU with hidden size 64; early stopping on validation loss (patience 6, at most 30 epochs).
- **Evaluation:** Episode-disjoint training, validation and test splits (70 / 15 / 15 %, 3,850 / 825 / 825 episodes). The split is the one `train_gru_ppo.py --seq-len 20 --seed 42` draws, reused for every sequence length and seed, so every model is scored on the same 825 test episodes.
- **Ablation:** Sequence lengths of 1, 5, 10, 20 and 50 observations, each trained on seeds 42, 43 and 44 (CPU).

The best epoch varies between seeds (N=10: 3 to 9; N=1: 17 to 29), so single-seed differences of a few points between sequence lengths are not meaningful.

## Key Findings

1. Observation histories substantially improve task identification over single observations: about 63 % → 83 % task-episode macro accuracy from N=1 to N=5.
2. Beyond N=5 the gain is small: N=10, 20 and 50 lie within about 0.5 points of each other (84.9–85.3 % mean), and their seed ranges overlap. No sequence length above 10 is better than another on this data.
3. A single observation already identifies several tasks well above chance (1/9): the start states differ between tasks (each task has its own environment and reset hook), so part of the accuracy comes from where an episode starts, not from behaviour.
4. `unlock` is the hardest class (24 % at N=1, 70 % at N=20). Its composite runs `get_key` and then `open_door`, so its windows look like theirs: at N=1 its windows go mostly to `get_key` (33 %) and `open_door` (26 %), and at N=20 a third of them (32 %) are still classified as `get_key`.
5. `get_key_yellow` and `get_key_blue` start from identical states and are separated only by behaviour; both reach about 72–84 %.

## Completion Status

**Completed:** Supervised GRU training, held-out evaluation, confusion-matrix analysis, and sequence-length ablation on three seeds.

**Not yet evaluated:** Task-switch recognition latency, old-task retention during sequential task introduction, and end-to-end AE–GRU integration.

These results establish the supervised task-identification baseline for subsequent integration with the continual and hierarchical RL architecture.

## Reproducing

From the repo root, in the `ens491` environment (datasets and checkpoints go to the gitignored `data/` and `models/`):

```sh
python -m scripts.collect_gru_ppo_rollouts --episodes 500 --output-dir data/gru/ppo_500
python -m scripts.train_gru_ppo --data-dir data/gru/ppo_500 --output-dir models/gru_ppo_500 --seq-len 20 --seed 42
# for SEED in 42 43 44, N in 1 5 10 20 50:
python -m scripts.train_gru_task --data-dir data/gru/ppo_500 --output-dir models/gru_task_s$SEED \
    --seq-len $N --seed $SEED --original-splits models/gru_ppo_500/gru_seq20_splits.json
python -m scripts.evaluate_gru_task --data-dir data/gru/ppo_500 --model-dir models/gru_task_s$SEED --seq-len $N
```

`evaluate_gru_task.py` writes `runs/v2/gru/task_seq<N>_s<seed>_metrics.json`. Device is `cpu` unless `--device` is given.
