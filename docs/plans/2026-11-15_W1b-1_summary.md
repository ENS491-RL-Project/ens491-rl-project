## Verdict: W1b-1 passes (3 of 3 seeds)

**`{2,2} unlock_pickup` is STABLE under 0004 (argmax) on 3 of 3 seeds, with a child frozen under
0014 (`Proposed`).** Each seed's fresh row (env seeds 54000–54499, argmax) is 486/500 = 0.972
(Wilson 95 % 0.954–0.983); the rule needs STABLE and ≥ 450/500 on at least 2 of 3.
Disclosure, in the same paragraph as the result: the ten argmax handoff rates were known when the
freezing rule was written, so the rule and the seed it selected (45) are not blind; every
`unlock_pickup` result was unseen until step 3.

Three limits, stated with the result:

- **The three seeds are one result.** The three trained selectors act identically: the same
  stopping scores from the second evaluation on (48, 48), the same held-out 49/50, and fresh rows
  equal episode count for episode count (486/500, mean 31.05 env steps, 14 timeouts). The plan said
  so in advance ("not independent": same stopping seeds, same frozen children).
- **This does not show that the selector learned something the mask does not give it.** Each run
  reached STABLE after two policy updates (1,536 decisions). Random selection among available
  children scores 0.718–0.750 on the same 500 fresh seeds; under the strict mask the random arm ties
  the learned selector (49/50 held-out). The learned selector's gain is steps: 31 env steps per
  episode against 139–148 for random over available (about 4.6×). This is the H-5/H-6 masking
  result again, on a third task.
- **What it shows is reuse.** `{1,1} unlock_door`, trained on Unlock, runs untouched as a child on
  UnlockPickup, a task flat PPO did not solve in 3,000,320 steps (0/50 on the same 50 held-out
  seeds, same mode). The remaining 2.8 % fresh loss is in the chain before the handoff (the ceiling
  gate below), not in the selector.

Flat comparison: on the 50 held-out seeds 20000–20049 only. The fresh 500-seed row has no flat
counterpart, because no flat model was saved (roadmap decision 4 stays with W1b-2).

## Deviations and choices not fixed by the plan

- **Step 1, first smoke run:** the script read the chain-step count from
  `chain_env_steps_in_resets.during_training.chain_steps`; the field is one level deeper
  (`…during_training.training_envs.chain_steps`), so the smoke run stopped with a `KeyError` after
  P2 and P1, before anything was saved. Fixed, smoke rerun clean, then the real run. No effect on
  any result; the value in the meta is 372,063, as in the plan.
- **Step 2:** the ceiling gate's output file name (`runs/v2/w1b_unlock_pickup_gate.json`) was not
  named in the plan. Step 3 refuses to train unless that file says the gate passed.
- **Step 3:** run in a separate git worktree (the frozen child copied into it, its sha checked on
  load), with `ENS491_RUNS_ROOT` pointing at the main folder's `runs/training/` so the run-store
  archives stay; outputs copied back unchanged. The three logs are committed with `git add -f`
  (`*.log` is ignored; `runs/v2/` already tracks logs this way).
