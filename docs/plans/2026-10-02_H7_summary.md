## 3. Why the stop, and what deciding it needs

A2 reads: "not stable → report, not frozen, H-7.3 onward blocked → **stop and report**". The plan
gives `pickup_box` no fallback (only `move_blocker` has one) and forbids a per-node stopping rule.
Every remedy is therefore a spec change, and the call is the author's. The measured options:

1. **More budget.** All three curves were rising. This is a plan change, since budgets are fixed in
   advance.
2. **A different reset distribution.** For example, anchor the start pose in the left room, where the
   real handoff happens. That changes the hook's spec string and therefore v2 §11 T6 (A.1).
   The diagnosis says the current hook spends its mass on states the parent never produces.
3. **Report it as is.** A primitive that needs drop-then-pickup plus a door crossing, under a sparse
   own-goal reward, did not learn in 600,000 steps. That is itself a cost the reuse argument has to
   carry.

Whatever is chosen, the full-hand rows already say BlockedUnlockPickup will probably need H-7.5's
rebuild branch: `get_key` mistakes the ball for the key.

## 5. Deviations from the plan

1. **Solvability audit by exhaustive search, not flood fill.** The plan's proxy ("a cell adjacent to
   the box is reachable") flags 13/500 `pickup_box` layouts on UnlockPickup, where the key lies on the
   open door's only approach cell, and 3/500 `move_blocker` layouts, where the agent is boxed in by
   the ball and the key. All of them are solvable by picking up the obstacle. A breadth-first search
   over MiniGrid's own rules (forward, pickup, drop, toggle) finds **0/500 unsolvable** for both
   hooks. It was checked against a walled-in agent and a wrong-colour key, which it correctly calls
   unsolvable. Both counts are in the JSON.
2. **`relocate_blocker` has an acceptance guard.** The ball may not cut the agent off from the key,
   the door, or a reachable box. It was there from creation, under the planned spec string
   `relocate_blocker`.
3. **V4 over 400 trials** (the plan used 121 and 68).
4. **CPU priority.** The flat baselines ran at BelowNormal while critical-path nodes trained, so the
   sequential path got the capped CPU. It changes wall time only, never results.
5. **Extra files.** `scripts/h7_nodes.py` holds every H-7 node spec, so a spec cannot drift between
   trainer and loader. `scripts/h7_composite.py`, `train_unlock_pickup.py` and
   `train_blocked_pickup.py` are written for H-7.4/H-7.6 and have **not been run**, not even with
   `--smoke`, because they need a frozen `pickup_box`.
